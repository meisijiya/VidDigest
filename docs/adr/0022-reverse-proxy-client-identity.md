# ADR 0022：反向代理的来源身份（边缘覆盖 X-Forwarded-For，后端取末段）

## 决定

限流与并发闸门用的「同一个来源」由**两边共同**决定，两边都要对：

1. **边缘代理覆盖这个头**：`frontend/nginx.conf` 的 `location /api/` 块里是
   `proxy_set_header X-Forwarded-For $remote_addr;`——**覆盖**，不是追加
   （不用 `$proxy_add_x_forwarded_for`）。头里只留一个权威地址。
   `X-Real-IP` 保持不动。
2. **后端取末段**：`backend/ratelimit.py` 的 `client_identity()` 在直接对端可信
   （回环或私网段，前面确实有反向代理）且请求带 `X-Forwarded-For` 时，身份取
   这个头的**最后一段**；没有这个头就用直接对端地址；直接对端是公网时**完全
   忽略**这个头。

**为什么是末位**：标准边缘代理用的是**追加**语义（`$proxy_add_x_forwarded_for`）——
客户端带来的值排在前面，代理自己看到的对端地址 `$remote_addr` 追加在**最后**。
于是末位才是权威地址，客户端自报的那些段（可以随便伪造）失效。取首位等于让
攻击者自己挑限流桶的键：改一个头就换一个桶，限流器就成了摆设（工单 #94）。

**为什么边缘还要覆盖**：追加语义下客户端伪造的那几段虽然不再影响分桶，却仍然
留在头里——读这个头的别的东西（访问日志、未来的别的服务）读到哪一段取决于它们
自己怎么写。覆盖让这件事变成「头里没有假值」，也让后端取首段还是取末段都得到
同一个答案。两边各自不依赖对方的假设：一边被改坏，另一边仍守得住自己的那半。

## 为什么

- 工单 #94 的实测：边缘用追加语义 + 后端取首位 ⇒ 客户端自带的伪造地址成了限流
  桶的键 ⇒ 每次换一个头就换一个桶，连打 25 次 `/api/parse`，429 命中 **0/25**，
  限流被完全绕过；不带头时第 21 次起正常 429。
- **限流是这一层唯一的护栏**：这些端点不挂鉴权，额度护栏只管模型调用那边。护栏
  被一个 HTTP 头绕过，等于没有护栏。
- **不能改成「只信头部」或「只信对端」**：只信对端会把同一 NAT 后面的人算成一个人
  （粒度变粗但仍然安全）；只信头部等于把限流桶的键交给攻击者。取末段是在
  「粒度够细」与「键不可控」之间唯一站得住的位置。
- **为什么把责任分给两边**：只改后端，边缘的头里仍留着伪造前缀；只改边缘，后端
  还得继续假设「代理会追加」这个约定。两边都钉住，任何一边被改坏都还有另一半
  兜着——这与本仓「结构性约束用变异确认它真能变红」的判据是同一件事。

## 代价

- **前置多一层 CDN / 反代时，粒度会变粗**：那时 nginx 看到的 `$remote_addr` 是
  **那一层代理的地址**，不是真实客户端。于是所有用户落进同一个桶 → 正常的用户
  互相误伤（集体 429）。这时必须改用 nginx 的 **realip 模块**
  （`set_real_ip_from` + `real_ip_header`）把真实客户端地址还原出来，再让
  `proxy_set_header X-Forwarded-For $remote_addr;` 覆盖转发。**没有 realip 就硬上
  一层 CDN，等于把绕过换成误伤**——两个都是坏结果，但后者更难查（它长得像
  「服务不稳定」）。
- **直连后端端口时，单段 XFF 仍可自报**：绕过 nginx 直连后端（对端是回环/私网）
  并带一个单段 `X-Forwarded-For` 时，后端取到的末位就是那个自报值。**因此后端
  端口不得对外暴露**——它只能在容器网络或本机回环上可达。
- **粒度按 IP**：同一个 NAT 后面的人算一个人（与 ADR 0020、ADR 0021 一致）。
- **换边缘实现要重新对表**：真实 IP 怎么传到后端是边缘平台的事。换成别的网关/
  网关配置时，「头里只留一个权威地址」这条约定要重新确认一次。

## 推翻条件

- 前置代理链变成多层且无法用 realip 还原真实地址（那时限流键可能要换成
  API key / 账号维度，而不是 IP）。
- 边缘不再是 nginx（换成别的代理或云网关）：覆盖语义要由新平台提供。
- 需要按用户而非按来源分桶（那时 XFF 这条链整体不再相关）。

## 后果

- 与 [ADR 0020](0020-public-endpoint-rate-limit.md) 的关系：0020 定了「按来源 IP
  限流、公网直连不采信 `X-Forwarded-For`」，但**没定**采信哪一段；0022 补上这一段，
  并把「头里只留一个权威地址」的责任分给边缘。0020 的决定段是历史记录，不改写。
  与 [ADR 0021](0021-public-endpoint-concurrency-gate.md) 共用同一个
  `client_identity` 判定——两道闸门的口径必须一致。
- 行为由 `backend/tests/test_ratelimit.py`（21 条）与
  `backend/tests/mutation_ratelimit.py`（10 个变异）钉住：其中一条变异专门把
  后端改回取首段、另一条专门把边缘改回追加语义，两条都必须转红。
- 端到端守卫是 `scripts/ops/check_xff_bypass.py`：从栈**外面**连打 25 次带唯一
  伪造头的请求，至少要出现一次 429（`detail.code == rate_limit`），否则退出码 1。
  它在 CI 的「生产构建」作业里跑——那一步起的是真镜像、走的是真 nginx。
- 运维口径（信任模型、部署时怎么配、怎么自检）见 `docs/OPERATIONS.md` 第 10.4 节。
