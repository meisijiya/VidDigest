# 平台模型清单入库，平台凭据与用户自带凭据都留在 .env

新增表记录「有哪些厂商、每个厂商开放哪些模型、哪个是平台默认」。
平台自己的 API Key **仍留在 `backend/.env`**，用户自带密钥（BYOK）**完全不动**。

## 这条要解决的其实是一处已存在的不一致

改动前实测：模型清单**前后端各写一份，且内容已经不一致**——

- `frontend/src/lib/byok.js:38-88` 硬编码 7 个厂商（platform / bailian / deepseek / moonshot / openai / ollama / custom）
- `backend/summarizer.py:706-709` 只认 2 个（bailian / deepseek）
- 默认模型也不一致：前端 `qwen-plus`（`byok.js:50`）vs 后端 `qwen-turbo`（`summarizer.py:707`）

后端原本**没有**「可用模型清单」这个概念，`model` 只是一个字符串字段，用户留空就回落平台默认。
所以本决策不是「新造一个功能」，而是**给一个已经存在且正在漂移的事实建一个单一来源**。

## Consequences

**与 ADR 0004 的边界**：0004 管的是「用户自带凭据不落盘」，本 ADR 管的是「平台清单可配置」。
两者相邻但不重叠——本决策**不引入任何凭据持久化**。
`UserCredential` 仍是纯内存、单请求生命周期的封装，唯一的真值出口仍是 `reveal()`。

**`byok.js` 里那段注释是一个已记录的取舍**：
「刻意不放 DeepSeek 之外的聚合平台：清单一长就会过期」。
清单入库后这个理由依然成立——表里的行同样会过期。但漂移从「两份硬编码」变成
「一行可增删的记录」，且后台改完立即生效，不需要发版。

**凭据仍在 .env 的代价**：新增平台厂商仍需改环境变量并重启。
这是刻意的——凭据持久化需要引入加密方案与密钥轮换，不属于本轮范围。

## Considered Options

- 清单 + 平台凭据全部入库（DB 加密存储）：后台能直接换 Key，但需引入加密方案，
  且会让「服务端持有平台凭据」成为常态，与 0004 相邻却未被其覆盖。
- 后台表单提交后写 `.env` 或配置文件：不动 schema，但要处理运行中写文件、文件权限与并发写，
  且与「凭据只从环境变量载入」这条既有边界混在一起。
- 只读展示当前生效的厂商/模型：零 schema 改动，但等于诊断页，
  既解决不了已存在的前后端不一致，也谈不上「管理」。
