# 卡片展示字段在占位时写入，不由前端事后回填

`videos.video_title` / `videos.cover_url` 由**发起解析的那个请求**带过来，
服务端在 `reserve_video` 建出占位行的同一条 INSERT 里写入；
不再依赖解析成功后前端另打一次 `POST /api/community/cards`。

## 为什么原来的路走不通

回填端点要求 `status = 'ready'`，而占位行在解析完成前一直是 `pending`。
前端那次调用紧跟 `/api/parse` 成功发出，那一刻这一行**还不存在**
（它要等用户点「AI 总结」才被 `reserve_video` 建出来），于是那次 UPDATE
永远匹配 0 行，返回 `{"success": true, "updated": 0}` 而客户端连这个 0 都不看。

首次解析者填的标题与封面因此永远写不进去，卡片实际由**第二个访问者**补。
连带后果不是观感问题：`videos_fts` 索引 `video_title`，而绝大多数行该字段是空串，
社区按标题搜索基本失效，真正可搜的只有 `tags` 与 `video_url`。

## Consequences

- 少一次往返：建占位与写卡片是同一条语句。
- `videos_fts_ai` 是 AFTER INSERT，占位时写进去的标题**当场**可检索。
- 接管别人的陈旧占位时**只填空不覆盖**（`CASE WHEN COALESCE(col, '') = ''`）。
  那里写的是别人已经建好的行，无条件覆盖会让先到的那个人被后来者悄悄改掉卡片标题，
  与 ADR 0006 / 0007 的「先到先得」直接冲突。判据必须带 `COALESCE`：
  这两列可空，而 `NULL = ''` 求值为 NULL（不是 True），裸等号会让老库里的
  NULL 行永远填不上——症状与「修复没生效」完全同形。
- 代价：标题准确与否取决于 `/api/parse` 的返回。平台不给标题就是空串，
  与旧行为同形，不引入新的失败模式。
- `POST /api/community/cards` **保留**：修复之前建出来的那些空标题行仍需要它。
  它的用途收窄为「修老行」，首次解析时拿到 `updated: 0` 是**预期结果**而不是失败，
  不值得为它每次首解析都报一次错；但请求本身失败（网络 / 401 / 500）必须留痕，
  那才是真正会让人查半天的问题。

## Considered Options

- **挪到 `complete_video` 之后回填**：等于多一次写入；而且首次解析者与第二个
  访问者之间的窗口仍然在——第一个人解析失败时没有人回填，那一行就永远是空标题。
- **`/api/summarize` 成功后前端重试 `publishCard`**：把时序修在客户端，
  于是同一件事要在前后端各写一遍；且用户可能在重试前就关掉页面。
- **占位时一并写入（本 ADR）**：判定点只有一个（`reserve_video`），
  且正确性不依赖前端在某个时刻发起第二次请求。
