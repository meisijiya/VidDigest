# ADR 0020：公开端点按来源限流（429 + Retry-After）

## 决定

不挂鉴权的端点——`/api/parse`、`/api/download`、`/api/direct-url`、
`/api/proxy/thumbnail`、注册、登录——按**来源 IP** 限速。超了回 **429**，
响应带 `Retry-After`（还要等几秒），响应体里的 `error` 说清是「服务器限流」。

计数是**固定窗口**、**进程内**的：窗口默认 60 秒，上限按「这个端点一次要花多少
服务器资源」排——下载 10（要落盘，最重）、解析 20（出网抓取）、直链 30、
缩略图 60（轻量出网）、登录 10（bcrypt 是慢哈希）、注册 5（写库）。
全部可用 `VIDDIGEST_RATE_LIMIT_*` 覆盖；某个桶设成 **0** = 这个桶不限流。

「同一个来源」怎么算：按来源 IP。只有直接对端是回环或私网段（前面确实有个反向
代理）时才采信 `X-Forwarded-For` 的第一个地址；**公网直连时不采信**。

## 为什么

- 这些端点**不挂鉴权**，谁都能打；而成本全在服务器这一侧：出网抓取、落盘、
  bcrypt 计算。已有的额度护栏只管模型调用那边（每日解析 3 / 追问 10），
  管不到它们。
- 没有这层时，一个脚本就能把带宽与 CPU 打满，而日志里全是「正常请求」——
  这是**没有症状**的缺陷，最难发现。
- 为什么要回 `Retry-After`：让客户端知道该等多久，而不是自己猜着重试。
- 为什么按 IP 而不是按用户：这些端点大多在登录之前，没有用户可按。

## 代价

- **单机、进程内**：进程重启计数就清零；多实例部署时每个实例各数各的。
  要多实例正确，得把计数换成共享存储（Redis），那是另一件事。
- **限速不是并发闸门**：同一时刻的并发请求数没有闸门，限流只挡「速率」。
- **按 IP 分桶有副作用**：同一个 NAT 后面的人算一个人。宁可少算，也不能让
  「改一个头就换一个身份」成为常态。
- 多一个进程内状态：清零只发生在进程重启，没有对外的清理入口。

## 推翻条件

- 需要多实例部署（要把计数换成共享存储，并处理计数表在多实例间的可见性）。
- 需要挡的是并发而不是速率（要连接数限制或排队，限流器解决不了）。

## 后果

- `backend/ratelimit.py` 是这层的唯一实现；六个端点各自挂一个桶
  （`rate_limit("/api/parse")` 这样的依赖，装配时桶名写错会直接报错，
  不会变成「端点没挂上限还不吭声」）。
- **桶名就是被限的那个端点路径**（`/api/parse`、`/api/login`…），不另起一套
  抽象词：`parse` 是「额度种类」的名字（`database.QUOTA_KINDS`），限流桶若也
  用这个词，会撞上「额度种类只有一处枚举」那条结构守卫
  （`backend/tests/test_quota_kinds_single_source.py`）。改桶名而不是给守卫加
  豁免，是为了让那条守卫对所有后来人照样有效。
- 上限是环境变量而不是代码常量——改配置不用改代码，也不用改完再发一版。
- 前端把「服务器限流」与「平台风控」分开说（`frontend/src/lib/errors.ts`）：
  自家限流说成平台风控，用户就会去怪视频站、反复重试，反而触发得更狠。
- 429 的错误体带机器可读的 `code`（`rate_limit`），中文 `error` 只给人看。
  两端靠文案对齐是脆的：改一次文案，前端就把自家闸门说成平台风控。`code`
  是协议，前端先认它，老后端没给 `code` 时才退回认文案。
- 行为由 `backend/tests/test_ratelimit.py`（15 条）与
  `backend/tests/mutation_ratelimit.py`（8 个变异）钉住；运维口径见
  `docs/OPERATIONS.md` 第 10.4 节。
- 「采信 `X-Forwarded-For` 的哪一段」由 [ADR 0022](0022-reverse-proxy-client-identity.md)
  收紧：边缘代理必须**覆盖**这个头，后端取**末段**。上面那两份文件的条数是 0020
  当时的快照，当前的条数与规则以 `backend/tests/test_ratelimit.py`、
  `backend/tests/mutation_ratelimit.py` 与 ADR 0022 为准。
