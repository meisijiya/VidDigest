# 社区审核：后台可改标签、可删条目（只删社区，不删用户记录）

ADR 0010 把社区页签定成只读，理由是「不做下架」。本 ADR 推翻那一条。

## 推翻 0010 的哪一部分

**推翻**：`GET /api/admin/community` 只读这一条。

**保留**：`videos.parsed_by` 是弱引用、社区内容必须在解析者注销后留下来。
这条与「管理员主动删一条违规内容」是两件事，本 ADR 不碰它。

## 删条目的语义：只删 videos 一行，用户的解析历史一行不动

这是本 ADR 最重要的一条，也是用户明确要求的。

删掉社区条目之后：

- 该视频**不再出现在**公开社区列表（行没了，不是加了个过滤条件）
- 解析过它的用户**在自己的「历史」里仍看得到**自己那条记录

它在数据上成立，不靠约定，靠 schema：全库只有两处外键，都是
`REFERENCES users(id)`（`orders` 与 `parse_history`），**没有任何外键指向
`videos`**；`parse_history` 与 `chat_messages` 都不引用 `videos`。

**这个论证是有失效条件的**：哪天给 `videos` 加上被引用的外键，上面这段连同
`delete_video_record` 里的注释一起作废。注释里写明了这一点，不是客套。

级联删掉 `parse_history` 等于替用户决定「你解析过的东西不许留」。解析历史是
**用户自己的数据**，不是社区内容的附属品。对照 ADR 0012 的 `delete_user`
（有名下内容就 409、绝不级联），方向一致。

## 允许删 pending 占位行，不加 status 守卫

代价先说：一次**正在进行的**解析会因此在 `complete_video` 处拿到 rowcount 0，
而那个函数的 docstring 明写「由调用方报警而不是静默当作成功」——所以后果是
**响亮地失败**，不是数据悄悄写丢。

仍然允许删的理由是后台没有别的清理出口：

- 占位行**不带任何「我还活着」的凭据**。`updated_at` 只在被写时才会动，
  解析过程本身不续租，所以「进程正在跑」与「半小时前崩了」在表里是同一种形状
- 唯一近似的判据是 `VIDEO_PENDING_TTL_SECONDS`（默认 30 分钟），但它只活在
  `reserve_video` 的接管分支里：同一个链接被**再次解析**时才会顺带回收陈旧占位。
  后台这个页面拿不到它
- 于是禁止删 pending 的实际后果是：崩掉的占位行除非有人恰好重新解析那个链接，
  否则后台永远清不掉它

选「响亮地失败」而不是「制造静默且永久的死条目」。

## 标签：管理员这条路 fail-fast，模型那路继续容错

沿用 ADR 0005 的固定词表。管理员提交的值里只要有词表外的，就 **400** 并在
detail 里点名被拒掉的是哪几个；空数组 400；超过 `MAX_TAGS` 400。

这与模型路径相反——`validate_tags` 在模型给出词表外值时回落到「其他」，
因为「模型选不出来」是**模型的问题**，只用于排查日志。而管理员提交词表外值是
**请求错误**：把「AI编程」静默变成「其他」，等于把打错字藏起来——管理员以为改好了，
分类页上却多出一条「其他」，真正想要的分类没设上。

顺序由词表说了算（`validate_tags` 的输出原样透传），不按请求的书写顺序：
同样的标签集合换个顺序提交，展示就会抖一下。

`validate_tags` 对超额是**截断**不是报错。管理员明确给了 4 个，我们要的是
「多了 1 个」这个信息，所以上限在端点先判掉，不让它走到截断。

## 词表只有一份真值：新增 GET /api/admin/tags/vocabulary

前端要渲染勾选框，就得知道词表。**不在前端抄第二份**。

`CommunityPage.vue` 早就立过这条规矩——它的标签筛选是「从已加载的卡片汇总」，
明确写着「不额外维护一份标签词表」。在后台再抄一份就是漂移本身：词表一改，
两个地方各活一份，分类页上就会出现模型永远不会产生的标签。

所以加一个只读出口，`maxTags` 也从常量取而不是前端数 `selected.length`。
保留分组是因为 `tags.py` 的注释写明分组「顺带说明标签的适用语境，能少一些
误选」；摊平就把这个信息丢了。

前端有一条断言专门守这件事：模板里出现任何一个词表内的标签字面量就红。
（硬编码之后其余所有断言照样全绿，而漂移已经发生——同 `byok.js` 硬编码
7 个厂商那一次。）

## 社区列表现已带 status（顺带关掉 #15 的一项）

`list_admin_community` 的投影新增 `status`（ready / pending）。这一条不是单独
加的，是删条目的前提：管理员得先分得清这一行是社区内容还是空占位，删之前才知道
自己在删什么。

`backend/tests/test_admin_api.py` 里那条**钉死字段集**的断言因此需要改，
它不是在给实现让路——钉死字段集的测试本来就会同时抓住「悄悄少一个字段」和
「悄悄多一个字段」，它是在正常工作。

## Consequences

1. **删除不可撤销。** 真删就是真删。要恢复只能从备份里捞。与 ADR 0012 的
   账号删除是同一档的代价，所以两步确认里写明了「不删用户的解析历史」——
   这份数据删完之后在界面上就看不见了，只能在点之前说。
2. **没有审计。** 谁在什么时候改了哪条标签、删了哪条视频，**查不出来**。
   这与 ADR 0012 登记的「账号变更无审计」是同一个缺口，现在范围变大了。
3. **重新解析会复活。** 删掉一条之后，某个紧跟着解析同一链接的人会重新建行
   （`reserve_video` 的正常路径）。这不是 bug，是「同一链接全站只解析一次」
   那条承诺的必然结果——它说的是同一时刻唯一，不是永远唯一。
4. **仍未做**：封禁 / 解封账号、改 VIP、社区视频的**下架**（软删除）。

## Considered Options

- **软删除**（`videos` 加 `is_hidden` 或 `status='removed'`）：能撤销、能审计，
  改动面也不大——只有一处 SELECT 条件。否决的理由是**用户明确要的语义是
  「社区不可见」**，而软删除会让「删了但还在库里」这件事在数据上与「没删过」
  难以区分；真删更简单也更诚实。若日后要加审计，更该加的是审计表而不是
  把行留下来。
- **级联删 parse_history**：一条 SQL 就能删干净，用户在历史里也看不到那条了。
  否决——那是替用户决定「你解析过的东西不许留」。
- **禁止删 pending**：见上面那节，会制造永久清不掉的死条目。
- **管理员也能自定义新标签**（扩词表）：那等于绕开 ADR 0005 的评审。
  扩词表走 `VOCABULARY_GROUPS` 的正常流程。
- **标签编辑用自由文本输入框**：省一个端点，但管理员打错字只能靠 400 才知道，
  而分类页的筛选器是按词表枚举的——打错字的后果是「设了个永远筛不出来的分类」。
