# ADR 0021：公开端点的并发闸门（与速率闸门分工）

## 决定

在速率闸门（[ADR 0020](0020-public-endpoint-rate-limit.md)）之外，给**重活端点**
再加一道**并发闸门**：同一个来源、同一个端点桶，**此刻还在跑**的任务数超过上限
就回 **429**，响应带 `Retry-After`，响应体里的 `error` 说清是「同时在跑太多」。

- 只挂 `/api/parse` 与 `/api/download`。其余四个公开端点（直链、缩略图、注册、
  登录）是秒级往返，不挂。
- 默认上限 **2**（每来源、每桶）。可用 `VIDDIGEST_CONCURRENCY_PARSE` /
  `VIDDIGEST_CONCURRENCY_DOWNLOAD` 覆盖；某个桶设成 **0** = 不限并发。
- 计数是**进程内**的：任务开始 +1、任务结束 -1，**异常路径也必须回落**。
  进程重启清零。
- **不排队**：超限的请求立刻被拒，不进等待队列。

## 为什么

- **两道闸门管的是两件事，谁也替代不了谁。** 速率闸门管「一段时间内来了多少次」：
  同一个来源一分钟只发一次、但那个任务跑十分钟，它一次都不会拦。反过来一秒发
  二十次、但每个都秒回，速率闸门会拦、并发闸门不会。只有速率闸门时，慢任务能
  一个个叠上来把带宽与 CPU 占满——这正是并发闸门要挡的。
- **两句话必须不一样。** 速率那道等一分钟就行，并发这道等前面的任务结束就行。
  混成一句话，用户就会白等一分钟。前端因此把两者分成两个分支
  （`frontend/src/lib/errors.ts`）。
- **为什么不排队**：排队的话用户等的是一个他不知道还要多久的队列，服务器端的
  内存还被请求堆着——那正是并发闸门要防的事。要排队就得有队列生命周期、取消、
  超时一整套机制，那是另一张票（见「推翻条件」）。
- **为什么只做最小版**：这一层护栏跑在所有公开端点的最前面，它自己挂了就等于给
  整个后端的启动加了一条新的失败可能。所以：不引新依赖（标准库够用）、不换算法
  （不做令牌桶 / 漏桶）、不碰速率闸门本身的算法与阈值口径、只挂两个端点。
- **为什么默认是 2**：一个来源同时跑两个重活就已经把带宽与 CPU 占满了，第三个进来
  只会让三个都变慢。宁可让用户等一下，也不要让整台机器被一个来源拖垮。

## 代价

- **单机、进程内**：进程重启计数就清零；多实例部署时每个实例各数各的。这与速率
  闸门是同一个边界（当前后端是单进程单 worker）。
- **默认 2 可能偏紧**：一个用户正常地同时解析两条视频也会被拒一次。缓解办法是
  调环境变量，不是加排队。
- **按 IP 分桶有同样的副作用**：同一个 NAT 后面的人算一个人——这一条与速率闸门
  一致，两道闸门必须保持一致，否则用户会看到互相矛盾的拒绝理由。
- **多一处进程内状态**：清零只发生在进程重启，没有对外的清理入口。

## 推翻条件

- 需要多实例部署（要把并发计数换成共享存储，并处理多个实例之间的可见性与
  原子加减）。
- 需要挡的是**排队**而不是拒绝（那要引入队列、取消与超时机制）。
- 需要更细的算法（令牌桶 / 漏桶 / 按权重计费）。
- 需要按用户或账号维度限并发（而来源 IP 分桶已经不够用）。

## 后果

- 两道闸门住在**同一个模块** `backend/ratelimit.py` 里，共用同一个「怎么算同一个
  来源」的判定（`client_identity`）。判断口径分了叉的话，用户会看到「速率说没
  问题、并发说太多了」这种自相矛盾的拒绝理由。
- 并发计数按 **(来源, 端点桶)** 分开：同一个来源在解析上的占用不会把下载也堵死。
- **桶名沿用「被限的那个端点路径」**（`/api/parse`、`/api/download`…），与速率
  闸门同一约定。不写 `parse` 那种短名——额度种类在 `database.QUOTA_KINDS` 里
  只有一处枚举，别处再写一遍会撞上「额度种类只有一处枚举」那条结构守卫
  （`backend/tests/test_quota_kinds_single_source.py`）。改桶名而不是给守卫加豁免，
  是为了让那条守卫对所有后来人照样有效。
- 桶名写错在**装配时**就报错（`concurrency_limit("/api/does-not-exist")` 直接
  `KeyError`），不会变成「端点没挂上限还不吭声」。
- 并发闸门是**异步生成器依赖**：占用发生在 `yield` 之前，归还发生在 `finally` 里，
  所以端点抛异常时名额也一定会还回来。漏还的后果不是「偶尔多拒一次」，而是那个
  来源之后的所有请求都被拒——一次崩溃就把自己锁在门外了。
- **名额在响应发出去之前就还**：下载端点拿到文件、准备好响应之后就把名额还了，
  剩下那段回传不该继续占着名额——客户端收到响应后可能立刻再点一次，那一次不该被
  自己上一个任务挡住。
- **并发 429 的 `Retry-After` 写 30 秒，它是保底下限不是承诺**：占着名额的任务可能
  跑几分钟（下载要出网 + 落盘），服务端那一刻不知道前面的任务什么时候结束。30 秒
  给的是「别立刻重试」的最小间隔。
- **下载端点的「用完即删」挂在响应对象自己的 `finally`** 上
  （`backend/download_artifacts.py` 的 `ArtifactResponse`），不挂在框架注入的后台
  任务上。工单 #90 的措辞是「清理挂在响应发送完成之后（框架后台任务）」，而用户故事
  要求「响应没走完时也要执行到」——客户端中途断开时，starlette `FileResponse` 末尾
  那句 `await self.background()` 根本不执行（它不在 try/finally 里）。两条要求只有
  挂在响应自己的 `finally` 上同时成立。
- 因此清理**不依赖 fastapi / starlette 的 background 注入语义**：框架升级不会让它
  静默失效。
- 行为由 `backend/tests/test_concurrency_limit.py`（24 条）与
  `backend/tests/mutation_concurrency_limit.py`（7 个变异）钉住；运维口径见
  `docs/OPERATIONS.md` 第 10.4 节。
- 并发 429 的错误体带机器可读的 `code`（`concurrency_limit`），与速率那道
  的 `rate_limit` 分开：前端要能分辨「来得太勤」与「同时在跑太多」——两者的
  用户动作不一样（等一会儿 vs 先结束前面那个任务）。文案只给人看，协议落在
  `code` 上。
