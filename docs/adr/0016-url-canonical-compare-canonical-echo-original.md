# 视频链接的归一：比较用规范值，回显用原文

`videos` / `parse_history` / `chat_messages` 三张表各加一列 `canonical_url`，
存 `canonical_video_url(video_url)` 的结果。**所有读出口按 `canonical_url` 比较，
所有写出口仍把用户手贴的原文写进 `video_url`，回显的也仍是原文。**

对工单 #25 的三问，答案依次是：**查询规范化**、**回显原文**、**by-url 靠映射命中**。

## 为什么是「查询规范化」而不是「入库规范化」

入库规范化会让 `videos.video_url` **不再是**用户手贴的原文，于是
`GET /api/community/videos/by-url` 的「精确定位」拿用户粘进来的原始 URL 去查，
会直接查不到——而按 #25 票面的说法，那恰恰是分享场景的主要入口。

查询规范化保留了原文，另开一列做比较，代价是多一列 + 一个回填迁移，
换来的是原文随时可取、随时可回显，且不依赖「未来所有写入路径都记得先归一」。

## 对工单 #6 两条承诺的影响

#6 定下的是「同一链接全站只解析一次」（`idx_videos_url` 精确比较）与
「先到先得的原文」（`publish_video_card` 守护）。本 ADR 的影响是：

- **「只解析一次」变强，且改由结构保证。** 落地前，同一个视频用带签名 / 不带签名
  两种 URL 解析会在社区里各占一行；落地后只有一行。
  注意是**新增**一条 `UNIQUE INDEX idx_videos_canonical ON videos(canonical_url)
  WHERE canonical_url <> ''`，**不是**把 #6 那条 `idx_videos_url` 移走——后者
  仍在 schema 里。两条并存，且 `idx_videos_canonical` 在非空场景下是**更宽**的那条
  （原文不同、签名不同也只许一行），`idx_videos_url` 唯一的额外作用是兜住
  `video_url` 为空的行——那种行 `idx_videos_canonical` 按 `WHERE` 明确不管。
  去重之所以必须跑在建索引**之前**，正是因为 `idx_videos_url` 挡不住这一种重复。
- **「先到先得」不变弱，但合并规则不是「一律取先到」。** 两条重复行往往互补，
  一律取先到会把后到那条已经解析好的内容丢掉。实际规则是：
  幸存者 = 更新（时间优先，id 兜底）；每个内容列取组内**最新的非空值**；
  `status` 取 ready 优先（合成 pending 会让明明存在的内容重新变成「还在解析」）；
  `created_at` 取**最早**（它是「社区里第一次出现这个视频」的时间）；
  `video_url` 取幸存者的——原文要留着**回显**（工单 #25 第 2 问）。
- **`parsed_by` 取幸存者的（= 最新的）。** 这是**产品语义**不是工程细节：
  它决定谁能重新解析这一条（`can_regenerate` 与 `complete_video` 的
  `WHERE parsed_by IS ?` 都落在它上面）。取最早的那个会让后来者永远无法接管。
  ⚠️ 若某个 canonical 组里有一行正在被覆盖（`regenerating_by` 非空），
  **整组跳过不合并**，并且本次**不建唯一索引**——去重不彻底时建唯一索引
  要么失败要么靠运气。宁可让 `idx_videos_canonical` 暂时保持普通索引
  （`PRAGMA index_list(videos)` 里 `unique=0`，可观察），下一次启动再试。
  绝不为了建一条索引去强抢别人正在进行的覆盖。
- **「原文」仍在库里**（`video_url`），所以这条承诺没有任何一处被删改。

## 回显与唯一定位在签名链接上的取舍（有意为之）

**签名仍然出现在访客响应里**，因为回显的就是原文。

规范化之后回显规范值就不再泄漏——但那样社区卡片点进去的地址就不是用户当初
分享的那个地址了。对临时分享链接来说，那可能正是持有人在意的那个地址。

### 2026-10-06 复核：这条取舍正式拍板为「维持原文」

当时留作独立决策的那一项（工单 #29）已复核并定案。复核查到一条本 ADR
初版没有的事实，它让取舍的比分差拉得更开：

**回显的那个 URL 是承重的，不是装饰。** `frontend/src/App.vue` 里点开社区卡片走的是
`handleParse(item.video_url)`，这条链一路到
`currentUrl` → `VideoSummary.videoUrl` → `/api/summarize` 与 `/api/history/save`。
也就是说**一个人点开别人分享的卡片，他自己历史里记下的就是卡片上显示的那个地址**。

于是「改成回显规范值」的真实代价不是访客看到的样子变了，而是：

- 每一个**点开卡片的下游用户**，自己历史里存的都是规范值，不再是他粘的那个地址；
- 分享者粘的那个地址，从第二个用户开始就没人再保留了——**逐层传播**。

反过来看泄漏本身有多大：泄出去的是 `?sig=…&token=…&exp=…` 这类**分享凭证**，
指向的是一条**本来就公开**的视频。凭证是「方便转发」的性质，不是私密数据。

两边的分量：维持原文的代价是「一个公开视频的分享凭证对匿名访客可见」；
改掉的代价是「每个下游用户的个人历史被改写，且逐层传播」。
**定案：维持回显原文。**

⚠️ 这也意味着「两者都给」并不是第三条路：同一个字段既负责展示、又是下游继承
的那个地址，另加一个字段等于签名仍然留在响应体里，泄漏一点没少。

这条现状被 `test_criterion_1_is_deliberately_not_met` 钉住：它断言签名确实还在
回显里（有人顺手把原文改成规范值时会红并要求还原），也断言比较用的那一份
确实不带签名。**要推翻这条决定必须同时改掉那条用例，不能只删它**——
它是「有人顺手改掉时会红」的唯一守卫。

工单 #25 票面第 4 项的答案是：**`test_community_url_echo.py` 里的 6 条一条都不转红**，
它们继续钉现状，且现在钉的是一件**已经复核定案**的事，
而不是一个还没来得及修的洞。

## 迁移策略

**一次性回填存量**，不是「只对新行生效」——库里已经躺着的那些行才是要救的那批。
顺序在 `init_db()` 里是硬约束：补列 → 回填 → 建普通索引 → 去重 → 升级成唯一索引。
老库里已经有重复行时 `CREATE UNIQUE INDEX` 直接失败，整段 abort，
症状是「本地好好的，一升级就打不开」。

补列之后还挂了三条 `AFTER INSERT` 触发器把空的 `canonical_url` 就地填上。
这一层兜底的理由：此前「这一列不空」只靠「三个写入路径都记得填」，那是约定不是
保证。任何一条直接 INSERT 的路径都会留下一批空值行，于是那些行在任何 canonical
查询里都匹配不上——**症状是「换个形态打开同一个视频，说没解析过」，而不报错**。

## 平台规则里的几处取舍

规则表在 `backend/url_canonical.py`。形态全部来自实测矩阵，不来自印象。

- **未识别的链接一律原样返回**，不猜。猜错会把两个不同的视频在库里塌成一行。
- **短链不在本 ADR 范围。** `b23.tv` / `xhslink.com` 的真实视频 id 根本不在 URL 里，
  必须先发一次网络请求解析跳转才知道自己是谁——那是产品行为变更或新增出网依赖。
  `youtu.be/<id>` **算在内**：id 就在路径里，映射到 `youtube.com/watch?v=…`
  是一次纯字符串替换，不需要出网。把它排除只会白留一个「同一个 YouTube 视频两行」的洞。
- **爱奇艺的 `.html` 后缀保留不抹掉。** 不带 `.html` 不掉进 iqiyi extractor、
  掉进 `[generic]` 兜底（AGENTS.md 实测）。抹掉它是改语义，不是去重。
- **B 站 `/list/` 合集页不归一。** 合集里每条视频在库里本该独立，
  归一会把整个合集塌成一行。
- **从 URL 抽 id 的正则必须锚定结尾**（`$`）。不锚定时 `/video/BV1TEST/a` 与
  `/video/BV1TEST/b` 都被截成 `BV1TEST`，两个**不同的**视频塌成同一个 canonical。
  这个 bug 从第 1 片就潜伏着，到第 3 片建上唯一索引才发作（后写的那个被当成
  同一个视频合并掉），由既有测试 `test_history_search_favorites.py` 抓到。

## Consequences

- **三张表都要这列。** `parse_history` 与 `videos` 按原文 JOIN 时，两人粘不同形态
  谁也 join 不上谁；而社区/追问都要靠「我解析过这个视频」把两边的行连起来。
- **`parse_history` 保留多行。** `idx_history_user_url` 仍然 UNIQUE 在
  `(user_id, video_url)`，用户两次粘不同形态就是两条个人记录——「社区只解析一次」
  说的是社区那一行，不是这一张表。
- **新增一张表要参与比较时，得记得给它也加 `canonical_url`**，并把表名加进
  `_CANONICAL_URL_TABLES`。这条目前靠代码审查守着，没有结构约束。

## Considered Options

- **回显规范值（签名不再泄漏）**：安全，但社区卡片点进去不再是用户当初分享的地址。
  真正的取舍点是「用户在意的是地址本身，还是地址背后的视频」。本轮选后者优先。
- **入库就归一**：省一列，但 by-url 与「原文可取」两个能力同时失效，见上。
- **短链一并归一**：需要出网解析跳转，把一个纯函数变成有副作用的网络调用，
  且失败时无法判断「不支持」与「网络不通」。拆成独立立项。
