# 管理后台纳入账号生命周期：建号 / 管理员标记 / 删号（有内容则 409）

ADR 0010 把「删账号」列进**明确不做**，并且在 Consequences 里写了理由：
后台不做写操作账号，所以不需要审计账号变更。

这条现在被推翻。推翻的理由不是「想做」，而是 0010 的论证里有一个**当时成立、
现在不再成立**的前提：那时后台只有「改额度」一个写操作，管理员要处理一个
测试账号或误注册账号时，唯一出路是进库改 SQL。随着后台有了真实的运维用途
（改额度、下架失败排查、模型清单调整），手改 SQL 从「偶尔的例外」变成了
「常规操作」，而它没有任何校验、没有回读、没有 409 前置检查。

## 推翻 0010 的哪一部分、保留哪一部分

**保留**：`videos.parsed_by` 是弱引用、社区内容必须在解析者注销后留下来。
`delete_user` 一行 `videos` 都不碰——所以「后台不能靠删账号来清理社区数据」
这条依然成立，也依然是 `community` 页签只读的原因。

**推翻**：「不提供账号增删与权限变更」。

## 删除语义：有内容就拒绝，绝不静默级联

这是本 ADR 最重要的一条。

`orders.user_id` 与 `parse_history.user_id` 都带 `REFERENCES users(id)` 且
**没有 ON DELETE**，而项目开着 `PRAGMA foreign_keys=ON`——SQLite 按 RESTRICT
处理。也就是说，删一个下过单或解析过视频的账号，数据库会直接拒绝。

我们把这件事在应用层做成一次**可解释的拒绝**而不是一个 500：

- 先查这两张表有几行，为非零就返回 **409**，body 带 `blockers: {表名: 行数}`；
- 前端把行数显示出来（`订单 2 条、解析历史 5 条`），管理员知道还剩什么要处理；
- **不做级联**。订单是支付凭证，解析历史是用户自己的数据。级联换来的是
  「后台一个按钮点下去」，付出的是「删错了没法恢复」——两边不对称。

`chat_messages` 没有外键，但必须跟着删：建表注释已经写明「会话记录应随该用户
一起消失，而不是变成孤儿行」。

## 两道自锁保护，以及为什么它们是「不可逆后果」级别的

- **不能删除自己正在用的账号。** 单管理员部署下，删掉自己之后就没有任何人
  能把自己加回来——只能进库改。这是本功能里唯一一条「点错了就永久锁死后台」
  的路径。
- **不能撤销自己的管理员权限。** 同上，发生在降权而不是删除。
- **不能把最后一个管理员降级。** 与上面同源，留作纵深防御。

## VIP 明确不在范围内

`UserAdminUpdateRequest` 只声明 `is_admin` 一个键，并设 `extra="forbid"`——
多传一个键整个 422，`is_vip` / `vip_expire_at` 也在其中。这不是随手加的严格，
而是项目范围边界里「新增测试不得锁会员行为」那条纪律在接口层的落法：
VIP 仍然只能由订单支付写入，测试里也有断言守着模板不出现 `is_vip`。

## `is_admin` 的类型：Any 是本文件的约定，但必须配校验器

`UserAdminUpdateRequest.is_admin` 声明成 `Any`，这不是随手写的。本文件里
`QuotaUpdateRequest` 与 `ModelUpdateRequest` 同样用 `Any`，理由写在它们各自的
docstring 上：声明成 `int` / `bool` 的话，非法值会由 pydantic 变成 **422**，
而额度与厂商两个端点的契约要的是 **400**——「参数不合法」与「请求体结构不对」
是两种不同的客户端错误。

代价是这个字段**没有任何类型保证**，所以必须由 `_as_admin_flag` 把关。少了它：

| 输入 | `bool()` 的结果 | 后果 |
|---|---|---|
| `{"is_admin": []}` | `False` | 空数组 = 静默撤权 |
| `{"is_admin": {}}` | `False` | 空对象 = 静默撤权 |
| `{"is_admin": "false"}` | `True` | **想撤权却静默提权** |

最后一行是这个洞最坏的面：调用方写了一个明确想表达「false」的字符串，收到 200，
权限反了。校验器**刻意不收字符串**——它只接受真正的 `bool`，其余一律 400。

### 建号与改标记的严格度不对称（刻意）

`UserCreateRequest.is_admin` 声明成 `bool`，由 pydantic 校验，非法类型得到
**422**；`UserAdminUpdateRequest.is_admin` 走校验器，得到 **400**。同一个字段、
两个端点、两个状态码，这是有意的：

**授予/撤销权限的那个端点，比建号那个端点更严。** 建号传错类型的后果是多一个
字段没设上；改标记传错类型的后果可能是权限反向。严格度应该跟着后果的不对称走，
不该跟着「看起来一不一致」走。

两条各有断言守着，并且变异确认过：拿掉校验器后 8 条新测试转红，且**这 8 条全是
新加的**——没有既有测试在兜底，也就是说在补上校验器之前，这个洞是真的没人管。

## 新号不预置额度覆盖

`create_admin_user` 只写 `email / password_hash / is_admin`。新号一律回落全局
上限，与公开注册完全一致。要单独放宽走额度那条路——在建号时偷偷给一份初值，
会让「这个号为什么和别人不一样」变成一条查不到来源的历史。

建号复用**公开注册同一套**校验（`validate_email` / `validate_password`）。
各写各的会出现「同一个邮箱后台能建、公开注册说格式不对」，而这种分歧只会在
用户投诉时才暴露。

## Consequences

后台现在有了**不可逆**的写操作。这带来两条后续要求：

1. **删除没有软删除兜底。** 真删就是真删。要恢复只能从备份里捞。所以
   `delete_user` 的前置检查宁可过严。
2. **账号变更需要审计。** 0010 说过「不需要审计账号变更」，那句话现在只对
   额度成立。当前实现**没有**审计日志表——这是已知的缺口，登记在工单里，
   不在这里假装它已解决。

## Considered Options

- 级联删除全部关联数据：省事，但删订单等于销毁支付凭证，不可逆。否决。
- 软删除（加 `is_active` 列）：最安全，改动面也最大（登录校验、JWT、
  每一条按 user_id 过滤的读路径都要跟着判）。当前规模下不值得，先留。
- 只做「停用」不做真删：绕开了 409 那个真问题（外键照样挡），等于把问题
  推到别处。否决。
- 把管理员标记塞进 JWT：与 0010 冲突，且撤权要等 token 过期。否决。
