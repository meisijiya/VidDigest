# ADR 0030：社区检索的正文进索引，2 字词走子串兜底

## 决定

**社区检索的索引列集合固定为 5 列**（`backend/database.py` 的
`_VIDEO_SEARCH_COLUMNS`）：

```
video_title, tags, video_url, summary_md, subtitle_text
```

- `mindmap_md` **刻意不索引**：导图文本与总结大量重复，进索引只是同一段话被
  索引两遍，体积再涨一分、召回不涨一分。
- 三个同步触发器（`videos_fts_ai` / `_au` / `_ad`）的列清单由同一份
  `_VIDEO_SEARCH_COLUMNS` 生成，不写死三处。写死的话，加列时漏掉一处就是某条
  写路径上的索引静默失效。

**老库的列集合与此不同时，重建整张索引表**（`_create_video_search_index`）。
FTS5 的外部内容表不支持 `ALTER ADD COLUMN`，加列只能 DROP 重建；实测
`DROP TABLE` **不会**带走建在它上面的三个触发器，留着就会在重建时报
`trigger videos_fts_ai already exists`。所以顺序是：先删触发器 → 删表 → 建表 →
建触发器 → `rebuild`。重建后存量行立刻可搜。

**按查询长度分三条路**（`search_community_videos`）：

1. **≥3 字** → FTS5 `MATCH` 短语，走 `bm25()` 排序。
2. **恰好 2 字** → trigram 够不着，走子串兜底 `_search_substring`：
   在**原始 `videos` 表**上 `COALESCE(v.<col>, '') LIKE ? ESCAPE '\'` 逐列 OR，
   列集合与索引列集合一致；顺序用时间倒序（LIKE 没有相关度可言）。
3. **1 字** → 判「太短」，不查，零命中。

`min_chars` 报**总下限 2**，`q_too_short` 在 `len(q) < 2` 时置位。URL 精确匹配
走等值，不受这个下限约束。

**检索质量进门禁第 11 关**（`scripts/eval/check_search_quality.py`）：结构轨判
索引列集合、三个触发器写的列、分词器；质量轨判固定语料上的 top-1 准确率、
正文词召回、2 字词召回与零误召回。语料与阈值同源于 `scripts/eval/corpus.json`。
**语料是合成的**：真实字幕是平台内容，著作权归发布方（ADR 0002），公开仓库不
收录真实正文。合成语料不代表真实分布，它保证的是**可复算**——同一份语料、同一
份阈值、同一份命令，任何人跑都得到同一个数字。

## 为什么

- **原先只索引标题、标签、链接三列，于是只出现在正文里的词一条都搜不到。**
  同一份 96 条查询语料上的实测：正文词召回 **0/51（0.0%）**；加上总结列是
  18/51（35.3%）；**总结与字幕一起**才是 51/51（100%）。字幕必须进索引：
  总结是模型压缩过的，字幕才是视频真正讲了什么。
- **退化的症状不是报错，是「搜不全」。** 接口照常返 200，搜标题也照常有结果，
  只有正文里的词悄悄搜不到。任何「功能正常」的用例都发现不了这种退化——
  它们断言的是「能搜到」，不是「该搜到的都搜到了」。所以判据必须落在**召回**
  上，而且要有可复算的语料。
- **2 字词不能靠 MATCH。** trigram 按 3 字符滑窗切，2 字中文词在 MATCH 路径
  恒为 0 命中；前缀写法（`MATCH "异步"*`）也救不了。实测前缀 MATCH 仍为 0。
- **兜底必须落在原始表上。** FTS5 的外部内容表上的 `LIKE` 会**穿过 content 表
  读值**：没同步进索引的行也会被 LIKE 命中，可见性口径与 MATCH 不一致。在原始
  `videos` 表上匹配，口径才与「社区里能看到的行」一致。
- **`LIKE` 的元字符必须转义。** `LIKE` 认 `%`（任意长）、`_`（任意单字符）、
  `\`（转义符本身）。实测「带 ESCAPE 且逐字符转义」与真值表完全一致；不带
  ESCAPE 时 `%`/`_` 变成通配符，搜「100%」会命中一切含「100」的行。
- **代价是索引体积。** 36KB → 68KB（约 1.9 倍）。换来正文可检索，这笔账划算；
  更大的代价是「列集合」从此成为一条必须守住的约束，所以才有第 11 关。
- **不进 init.sh 的判据是那三条**：要花钱、要联网、产出是质量不是对错。
  第 11 关不花钱、不联网、判据是确定的对错，所以进。

## 代价

- **索引体积翻近一倍**。视频多了以后，FTS5 索引是随正文线性增长的。
- **2 字兜底是 O(正文总量)的扫描**，不像 MATCH 那样走倒排索引。实测 400 篇
  ×12k 字的内存库里 LIKE 约 0.0015s，仍是毫秒级；但它不是可以放着不管的
  路径——社区规模上去之后它会先变成瓶颈。
- **兜底的排序没有相关度**，只有时间倒序。用户搜一个词，先看到的是更新的，
  不是更相关的。这是刻意的：硬排一个相关度会骗人。
- **合成语料不代表真实分布**。它保证可复算，不保证「线上也是这个召回率」。
  真实分布要靠线上数据评估，而那一条需要环境与隐私，不进门禁。
- **col 集合变成了一条会被违反的约束**。多写一列进 `_VIDEO_SEARCH_COLUMNS`
  就会让索引重建一次；漏写一列则触发器与索引不同步，症状是「那列的内容搜
  不到」。第 11 关的结构轨就是守这条的。

## 推翻条件

- 换掉 SQLite FTS5（换搜索引擎、换存储引擎、引入向量检索）。
- 社区规模大到子串兜底的扫描成本不可接受（那时它必须换成倒排或前缀索引，
  而不是加机器）。
- 字幕改为带时间戳的富结构（那时「子串匹配」的口径要重新定，索引列也可能要
  拆成「文本列 + 时间列」）。

## 后果

- `backend/database.py`：`_VIDEO_SEARCH_COLUMNS`、`MIN_SEARCH_TERM_CHARS = 2`、
  `_search_substring`、`_escape_like`、`_video_search_index_columns`；
  `_create_video_search_index` 多了老库重建分支。
- 写出口有覆盖：`backend/tests/test_search_index_upgrade.py` 从**真老库的三列
  索引**起步，钉住升级后列集合变 5 列、三个触发器都写全 5 列、正文词与字幕词
  升级后可搜、标题词**仍然**可搜（反向对照）、升级**幂等**。
- 读出口有覆盖：`backend/tests/test_community_api.py` 的 `TestSearchPaths`：
  正文专有词（总结里的、字幕里的）能搜到、2 字词走兜底能搜到、1 字词被拒、
  清空索引后 2 字仍能搜到而 3 字搜不到（证明兜底读的是内容表）。
- 门禁有覆盖：`scripts/eval/check_search_quality.py` 是第 11 关；变异确认见
  `scripts/mutation_search_index.py`（索引退回三列 / 触发器只写三列 / 分词器换掉，
  三个变异全部 KILLED，并带一条反向对照）。
- 术语：`GLOSSARY.md` 的「字幕」词条不再声称携带时间戳——社区里存的是纯文本。
- 简历口径：正文词召回 0/51 → 51/51、2 字词召回 0/27 → 27/27、索引体积
  36KB → 68KB，均由 `scripts/eval/corpus.json` + 上述命令可复算。
