# ADR 0027：思维导图固定为三层结构，存量导图靠写迁移重建

## 决定

思维导图是一棵**唯一根**的树，结构上限写死在代码里（`backend/mindmap.py`）：

- **深度 ≤ 3 级**：`#` → `##` → `###`。更深的标题连同它的子树被截断。
- **每支 ≤ 7 个子节点**：同一个父节点下的同层子节点（标题 + 列表叶子）最多 7 个。
- **全图 ≤ 30 个节点**（标题 + 列表叶子）。

「每层 ≤ 7」按**分支扇出**解释，不是「整层合计 ≤ 7」：后者会让三层最多只有
1+7+7=15 个节点，总节点上限 30 永远碰不到——那是一条死约束。扇出解释下三条
上限都非平凡，也都能被变异杀死。

配套三条：

- **提升根标题时后代同步下移**。模型常把根写成 `## 主题`、子节点写成 `### 要点`；
  只提升根而不动后代，后代就成了比根深两级的 `###`，在三层上限下整棵被截掉，
  节点凭空消失（5 节点 3 级只剩 3 节点）。清洗按**树深度**重算级别（子节点恒为
  父节点 +1），整棵子树的相对深度因此保持不变。
- **提示词里的 few-shot 样例必须是真的多层**（`backend/prompts/summarize_full.md`）：
  至少 2 个二级分支、有第三级、节点数在上限内。散文规则管不住形状——提示词自己
  写着「few-shot 的形状权重远高于散文规则」，那就得让样例本身是一棵多层的树。
- **退化兜底与存量重建用同一套规则**。模型给的导图为空或只有一层时，从**总结
  正文**重建（总结里的 `##` / `###` 标题是现成的结构来源）；库里已有的退化导图，
  由一条写迁移按同款规则重建。

## 为什么

- **退化发生在写库那一刻，不是渲染那一刻**。清洗在落库前就做，模型给的单层导图
  清洗后仍然只有一层，落库的就是一条光杆。前端再补救也救不回存量——「只对新总结
  生效」等于没改。存量只能靠一条写迁移重建。
- **形状靠样例教，不靠散文讲**。提示词里写着层级要求，但样例是一根分支时，模型
  照着样例输出。样例与规则冲突时，模型跟样例走。
- **重建的依据只能是同一行的总结正文**。它已经落在库里了，不用猜、不用重新调
  模型，也不会引入新的成本。
- **没有正文就保持原样**。宁可留一根光杆，也不拿别处的文字编一棵导图出来——
  编出来的结构会让读者误以为那是视频里的结构。
- **上限必须由代码执行**。提示词里的「不要超过 N 个」是建议，不是约束；模型不听
  时，截断是唯一的确定行为，而且截断规则必须写清楚（按文档顺序深度优先，丢弃的
  节点连同其子树一起丢，它后面的兄弟节点仍然保留）。

## 代价

- **截断会丢信息**。模型写超了，超出的分支整支被丢掉（而不是压扁成同级），
  用户看到的内容比模型给的少。
- **「每支 ≤ 7」是解释，不是原文**。工单写的是「每层 ≤ 7 节点」，本 ADR 选了扇出
  解释，因为整层解释会让总节点上限变成死约束。改解释就要同时改代码、常量与用例。
- **存量重建只覆盖退化（层级 < 2）的行**。已有层级的老导图不重写——重建依据是
  总结正文，用它替换模型原样产出的导图会丢掉原图独有的细节。没有总结正文的行
  一律原样保留。
- **前端仍有一份同款旧清洗逻辑**（`frontend/src/components/VideoSummary.vue` 的
  `sanitizeMindmap`）：它同样只提升 `##` 而不下移后代。后端现在保证落库的导图已经
  唯一根、无跨级，前端那份清洗因此是幂等的；但两边逻辑仍是两份，改规则时两边都要看。

## 推翻条件

- 换掉 markmap 或改前端渲染契约（层级语义、列表叶子的处理会一起变）。
- 产品改这三个上限的数值或含义（`backend/mindmap.py` 的常量与
  `backend/tests/test_mindmap_levels.py` 的字面量断言要一起改）。
- 决定改用「整层合计 ≤ 7」的解释（那要重新推导总节点上限，否则它是死约束）。

## 后果

- 规则落在 `backend/mindmap.py`（纯文本处理，不读库不调模型，所以 `backend/summarizer.py`
  与 `backend/database.py` 都能顶层 import 它而不绕成环）。
- `backend/summarizer.py` 的 `VideoSummarizer.clean_mindmap_markdown` 变成薄委托；
  兜底重建发生在 `summarize_full_stream` 里（SSE 与落库是同一份，所以两边同时修好）。
- 存量重建是 `backend/database.py` 的 `_migrate_mindmap_levels`，由 `init_db()` 调用，
  幂等：无正文不动、已有层级不动、只重建层级 < 2 的行。
- 行为由 `backend/tests/test_mindmap_levels.py`（结构与上限）、
  `backend/tests/test_mindmap_migration.py`（老库升级路径）与
  `backend/tests/test_summarize_routes.py`（提示词样例、落库层级）钉住；结构性约束
  由 `backend/tests/mutation_prompt.py` 里的 M1–M6 确认能变红。
- 运维口径（层级上限、截断行为、存量重建）写在 `docs/OPERATIONS.md`。
