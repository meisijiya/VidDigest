# ADR 0023：注册改为邀请码注册

> **修正（2026-10-25）**：本 ADR「后果」里「管理后台的邀请码区块是折叠的独立区块」
> 那一条已被 [ADR 0025](0025-invite-codes-management-page.md) 取代——邀请码管理
> 改成了独立路由 `/admin/invite-codes`。本 ADR 关于**注册语义**的部分
> （码怎么发、怎么消费、怎么失效、库里存什么）仍然有效。

## 决定

公开注册端点 `/api/auth/register` **必须带邀请码**。邀请码由管理员在管理后台发放，
不是用户自助领取。

- 新表 `invite_codes`（`backend/database.py` 的 `init_db()` 里建，老库另有升级路径）：
  `id`、`code_hash`（唯一，sha256 摘要）、`code_hint`（脱敏提示，前 4 后 4）、
  `created_by`（发放的管理员）、`created_at`、
  `expires_at`（空 = 永不过期）、`max_uses`（≥ 1）、`used_count`、`revoked`、`note`。
  **库里没有明文**。
- 三个管理端点（都在 `backend/admin_api.py`，鉴权一律 `Depends(require_admin)`）：
  `POST /api/admin/invite-codes` 发码、`GET /api/admin/invite-codes` 看列表、
  `POST /api/admin/invite-codes/{id}/revoke` 作废。
- **明文码只在创建响应里给一次**；列表出口只回脱敏提示（前 4 后 4，中间 `****`），
  它不是明文、不能用来注册。
- **码的组合空间 ≥ 128 bit**：字符集 25 个互异字符（去掉了易混字符：0/O、1/I/L、
  2/Z、5/S、8/B）× 28 位 ≈ **130 bit**。随机源是 `secrets`，不是 `random`——
  序列可预测的码等于没有码。
  这条下界是一条**可执行断言**（`backend/tests/test_invite_codes.py` 里独立重算，
  不抄实现里的常量）。
- 注册端点对邀请码做**四类**失败判定，而且各说各的话：不存在 → 「邀请码无效」、
  已作废 → 「邀请码已作废」、已过期 → 「邀请码已过期」、已用完 → 「邀请码已被用完」；
  缺码或空码 → 「需要邀请码」。全部是 400 + 中文 detail，不是 422。
- **消费是原子的**：校验邀请码、建用户、给码计数三件事在同一个 `BEGIN IMMEDIATE`
  事务里，任一步失败全部回滚。并发抢同一个 `max_uses` 为 1 的码，只能成功一个。
- 速率闸门（[ADR 0020](0020-public-endpoint-rate-limit.md)）仍然挂在注册端点上，
  **阈值与口径不动**。

## 为什么

- **速率闸门挡不住换 IP 的批量注册**——它按来源分桶，而来源可以换。邀请码是闸门之外的
  另一道：它把「能不能创建账号」从「知道邮箱密码」变成「手上有一枚别人给的码」。
- **谁发码决定了注册是「邀请」而不是「排队」**：码由管理员发放，管理员决定给谁、
  几个、多久有效。这比「自助申请 + 人工审核」少一整套审核队列运维，代价是想注册的人
  得先开口要码。
- **四类原因必须分开说**——用户据此能行动：「已用完」去找管理员要新的，「无效」去查
  自己有没有抄错，「已作废」去问管理员。混成一句「邀请码错误」，用户只能干瞪眼。
- **消费必须原子**——「码被消耗但账号没建成」和「账号建成但码没计数」都是用户看得见
  的错：前者让人白丢一枚码，后者让同一枚码能注册任意多个号。
- **明文只给一次，库里只存哈希**——管理员要把码复制给用户，所以明文在创建响应里
  给一次；但明文落库意味着「库被读走 = 所有还在用的码都归攻击者」，不需要爆破、
  不需要任何算力。所以库里存 sha256 摘要，明文只在生成那一刻出现。
- **码本身要够强**——只存哈希挡不住「组合空间小到可以枚举」：12 位、25 个字符的码
  即使用 sha256，快哈希一两个小时就能把整个空间扫完。所以码长与字符集按
  **≥ 128 bit** 定，断言是可执行的。
- **注册端的既有闸门不动**——速率闸门挡的是「来得太勤」，邀请码挡的是「没被邀请」。
  两件事各管一段，把速率闸门的阈值动一格既解决不了换 IP 注册，又会误伤正常用户。
- **为什么不动前端 api 层的签名**：`frontend/src/api/auth.ts` 的
  `register(email, password)` 是公共出口，不该为了某一个表单去改它。邀请码由组件在
  请求拦截器里一次性注入，请求结束就摘掉。

## 代价

- **注册多了一步**：想注册的人得先有码，公开试用没有了。
- **明文取不回来**：库里只有摘要，管理员复制走之后**没有任何办法**找回那枚码——
  发漏了只能作废重发。这是「库里不存明文」的直接代价。
- **列表里的脱敏提示是给人看的，不是给人用的**：它够管理员认出「这枚是我发给张三的
  那枚」，但它不是明文、拼不出完整码、拿它注册会得到「邀请码无效」。
- **哈希用 sha256，不用 bcrypt/argon2**：慢哈希是为「人选的弱口令」准备的；邀请码是
  130 bit 全随机串，没有字典可打，KDF 的「慢」在这里只换来注册延迟，换不来安全性。
  sha256 是标准库自带，**不引新依赖**。
- **邀请码不等于身份**：一个码可以给多个人用（`max_uses` 大于 1），
  事后无法从账号反查是谁用掉了它。
- **过期靠时间戳比**：`expires_at` 为空表示永不过期；坏值按过期处理（fail closed），
  宁可少让人注册一次，也不要让一枚坏码放行。
- **多一张表、多三组端点、多一处管理后台区块**：运维面变大了一圈。

## 推翻条件

- 要开放自助注册（那要另一整套：申请、审核、通知）。
- 要让邀请码兑换额度或会员（那邀请码就不只是「闸门钥匙」而是「资产」，语义要重定，
  与会员判定那条线也会缠上）。
- 要一个码绑定一个邮箱或一台设备（那要额外存绑定关系并在注册时校验）。
- 要多级邀请（邀请人自己也从上级拿码）——`created_by` 就从「记录」变成「一棵树」，
  得防环。

## 后果

- 邀请码的数据层在 `backend/database.py`，命名统一用 `invite_codes` / `invite_code_*`。
- 注册端点在 `backend/api_auth.py`；管理端点在 `backend/admin_api.py`。
- 老库升级路径是 `_migrate_invite_codes_table`（由 `init_db()` 调用）：表不存在就建，
  列缺了就补；表在但存的是老结构（`code` 列存明文）就**重建这张表**——把明文算成
  摘要填进新表，所以**升级前发出的码仍然可用**，升级后库里不再有明文。
  **从真缺表的老库、从真存明文的老库启动，都能自动升级。**
- 错误体统一是 400 + 中文 detail，四类原因四句话，不复用一句。
- 行为由 `backend/tests/test_invite_codes.py` 钉住，结构性约束由
  `backend/tests/mutation_invite_codes.py` 确认能变红；前端接线由
  `frontend/tests/auth-invite-codes.test.mjs` 钉住，变异追加在
  `frontend/tests/mutation-ui-fixes.mjs` 末尾。
- 邀请码的管理界面是**独立路由 `/admin/invite-codes`**（见
  [ADR 0025](0025-invite-codes-management-page.md)），管理后台里只留一个入口按钮。
  页面提供批量发放、状态筛选、分页与发放人回显；**明文只在刚发放的那一块出现**，
  列表里只有脱敏码。
- 管理员怎么发码、码的生命周期与常见失败原因，见 `docs/INVITE-CODES.md`。
