# 管理后台：同一 Vue 应用内的 /admin 路由，范围只读 + 改额度，不碰账号生命周期

管理后台是 `/admin` 路由下的独立界面，与主站**同一个 Vue 应用、同一套令牌、同一套组件**。
管理能力限定为四类：用户记录（只读）、用户额度（可改）、社区记录（只读）、AI 服务（模型清单可改）。

**明确不做**：封禁、解封、删除账号；社区视频的删除与下架。后者本就写在项目范围边界的「明确不做」里。

## 管理员身份：users 表加 is_admin 列，不塞进 JWT

`users` 表加 `is_admin INTEGER DEFAULT 0`，加列照抄 `_migrate_quota_columns` 已有的
`PRAGMA table_info` + 逐列 `ALTER TABLE` 套路。`auth.py` 新增 `require_admin` 依赖，
模式与现有 `get_current_user` 一致：**每次请求回查数据库**，不把角色塞进 JWT payload。

这样做的直接好处是提权与撤权即时生效，不必等 72 小时的 token 过期。
首个管理员由 `backend/.env` 的 `VIDDIGEST_ADMIN_EMAILS` 在启动时播种一次，之后在后台自行管理。

## 上线前必须先堵的洞

`auth.py:10` 的 `JWT_SECRET` 存在硬编码兜底默认值。漏配时服务静默使用这个**公开在源码里**的字符串，
任何人可据此伪造任意用户的 token。管理后台会让「伪造管理员 token」有实际收益，因此这一项
从「部署注意事项」升级为**上后台之前的前置条件**：缺失即启动失败。

## Consequences

**后台不做写操作账号，但要做写操作额度**，所以仍需鉴权，只是不需要审计账号变更。
`videos.parsed_by` 是**弱引用**（无外键，解析者注销后社区内容必须留下来），
这条既有设计意味着后台永远不能通过删账号来清理社区数据——与「不碰账号」的决定正好一致。

**后台是普通登录用户可见的入口。** 顶部导航对管理员显示「管理」，非管理员看不到；
即使手动访问，后端 `require_admin` 也返回 403。前端隐藏只做体验，不做安全边界。

## Considered Options

- 独立前端工程：隔离更强，但两套设计系统长期必然漂移，直接违背「UI 风格统一」的要求。
- .env 邮箱白名单：零 schema 改动、零回归风险，但运行时无法给人管理员，与「后台管理用户」自相矛盾。
- 独立后台账号表：隔离最彻底，但要再维护一套账号/JWT/找回流程，对当前规模过重。
- `role` 文本列（admin/user）：为将来多角色留门，但当前只有一种角色，属于提前设计。
- 后台同时管理社区视频下架：正面撞上项目范围边界里「社区视频的删除与下架属于明确不做」。
