# ADR 0015：覆盖闸门落库，不再依赖「后端只有一个进程」

- 状态：已采纳（2026-10-06，工单 #20）
- 相关：[ADR 0006 首次解析先到先得](0006-first-parse-wins.md)、[ADR 0007 本人可覆盖自己的那份](0007-owner-may-regenerate-own-summary.md)、[ADR 0002 字幕存库](0002-store-subtitles.md)

## 背景

覆盖（regenerate）路径**不占位**：重新解析的那几十秒里，旧内容仍然对所有人可见
（ADR 0007）。这不是疏忽，是承诺——把它改回 pending 会让复用者突然看到空白。

代价是同一个作者可以并发发起两次覆盖、两次都调模型、两次都扣额度，后写的那份
覆盖先写的那份。工单 #7 返工时为此加了一个闸门，但它是一个**进程内的
`set[str]`**（`api_summarize.py` 的 `_REGENERATE_INFLIGHT`）。

于是「后端必须单进程」从一句部署建议变成了**正确性硬约束**：`--workers 2` 把那
一个 set 劈成两份互不可见的副本，两个请求各自看见空 set、都判定「可以覆盖」。
后果是两次调模型、两次扣额度、结果互相覆盖——**不报错、不告警**。

`database.py` 里 `VIDEO_PENDING_TTL_SECONDS` 的注释早已把取舍写死：「两个人同时
调模型、同时扣额度——正好是本设计要防的那件事」，而那条防线在覆盖路径上掉线了。

## 决策

把闸门从进程内存搬到 `videos` 表的两列上，抢锁是**一条带条件的 UPDATE**。

```sql
UPDATE videos
   SET regenerating_by = ?, regenerating_at = ?
 WHERE video_url = ?
   AND status = 'ready'
   AND parsed_by = ?
   AND (regenerating_by IS NULL
        OR regenerating_at IS NULL
        OR regenerating_at <= ?)   -- TTL 之外才允许接管
```

`rowcount == 1` 即抢到。

### 为什么这一条语句就够跨进程

SQLite 串行化写事务。两个进程同时发这条 UPDATE，只有一个能拿到 `rowcount == 1`。
这**不是新机制**——`reserve_video` 依赖 `idx_videos_url` 唯一索引裁决首次解析，
用的就是同一件事。闸门只是把已经在这套代码里成立的那条性质用到了第二条路径上。

### 为什么落在 `videos` 上而不是单开一张锁表

抢锁要判的条件是「这一行归我」+「没人占着」，前者是 `videos` 上的列、后者也是
`videos` 上的列。拆成两张表就多一次跨表读，多出来的那次读与写之间就是一个窗口，
而那个窗口正是要消灭的失效形状。

### 为什么过期判定写进 WHERE 而不是先读后判

先读后判会在两个进程之间留窗口：两个进程都读到「没人占着」，都判定可以进。
写进 WHERE 就没有那个窗口——判据与写入在**同一条语句**里。

## 代价

1. **每次覆盖多两个写事务**（抢 + 放），而 `videos` 上的 `AFTER UPDATE` 触发器
   （`videos_fts_au`）无 `WHEN` 子句，于是每次抢放都会多触发一轮 FTS 删除+重建。
   没有为此改触发器：覆盖是用户主动的稀有操作，而改动触发器要重新验证
   「删光三个触发器全绿」那条既有护栏。为省两次 FTS 写去动它，代价大于收益。
   如果将来覆盖变成高频操作，第一件事是给触发器加 `WHEN` 子句限定在
   `video_title / tags / video_url` 三列上。
2. **TTL 必须大于一次覆盖的最长耗时**（字幕提取 + 一次模型调用），否则会在持闸者
   还在干活时把锁偷走，于是两个人同时调模型、同时扣额度——正是本闸门要防的那件事。
   `VIDEO_REGENERATE_TTL_SECONDS` 默认 1800 秒，与 pending 同量级但**是独立环境
   变量**：覆盖与首次解析的耗时分布不同，不该共用一个旋钮。
3. **持闸者进程被 kill 时锁会残留**，要等满 TTL 才能接管。这是「不重复扣费」与
   「可恢复性」的取舍，与 `VIDEO_PENDING_TTL_SECONDS` 完全同类，取前者。

## 为什么没有顺手改触发器

见上。这条留在这里，是为了下一个看到「抢一次闸门触发两轮 FTS 重建」的人知道
**这是有意留的**，而不是没人发现。

## 结果

「后端必须单进程」从**正确性硬约束**降级为**建议**（SQLite 写入串行化仍然是
扩容的真实瓶颈，但那是性能问题、不是静默失效）。`docs/OPERATIONS.md` 5.1.1
同步改写。

验证见 `backend/tests/test_regenerate_gate.py`，其中跨进程那三条是本 ADR 的关键
判据：它们起**真子进程**，且子进程抢到之后**不放**闸——于是断言不依赖竞态窗口，
永远不会 flaky，却仍然区分「锁在库里」与「锁活在某个进程的内存里」。
