# ADR 0019：容器化与运维证据链（compose 编排 + 脚本化备份巡检 + JSON 行日志）

## 决定

用 `docker compose` 把后端与前端编排成两个服务，并补齐「可运维」的五件可执行的东西：
镜像、编排、备份、巡检、日志。

具体取舍如下：

1. **镜像分层**：后端镜像基于 `python:3.11-slim`，装 ffmpeg（合并 DASH 分离的音视频流要用），
   以 uid 10001 的非 root 用户运行，附 `/api/health` 的 healthcheck。
   前端用两段式构建：Node 只出现在构建段，运行段只有 nginx 与静态文件。
2. **同源反代**：nginx 负责 SPA rewrite（`/admin` 直接刷新不 404），
   `/api/` 反代到后端并**显式关闭 proxy_buffering**——SSE 是长连接流，
   缓冲会把事件攒到结束才吐给前端，实时性就没了。
3. **数据与日志用 bind mount 挂到宿主目录**，不用命名卷。
4. **备份走 SQLite 在线备份 API**，拷完必须过 `PRAGMA integrity_check`，不过即失败；
   巡检脚本对健康端点、库完整性、数据目录占用、日志新鲜度、前端入口缓存、下载目录占用
   六项出判据，任一不达标退出码非零。
5. **日志一行一条 JSON**（`ts` / `level` / `logger` / `msg`），10MB×5 轮转，时间戳统一 UTC；
   接管 `uvicorn` 三个 logger 并把它们的 `propagate` 关掉。

## 为什么

- **为什么不用命名卷**：命名卷隔离得干净，但宿主机上的备份与巡检脚本就看不到容器正在用的
  那一份库和日志，脚本要么改成在容器里跑（要把脚本塞进镜像），要么就退化成「看起来在备份、
  其实备份的是另一份文件」。bind mount 让脚本与容器看同一个文件——
  「备份的是不是正在跑的那份库」不需要靠推断。代价是容器与本机开发共用一份数据文件，
  两者同时写会有 SQLite 锁竞争；本地开发时不要同时起容器和本机进程。
- **为什么备份不直接拷文件**：本库是 WAL 模式，运行中当前状态不全在主文件里，多出来的部分在
  `app.db-wal`。直接 `cp` 拿到的是缺事务的快照，恢复后会安静地丢数据。
  在线备份 API 拿到的是一致快照；`integrity_check` 校验不过就要让人知道——
  一份打不开的备份比没有备份更危险。
- **为什么巡检要非零退出**：巡检报告如果永远显示「一切正常」，它就只是输出文字，不是判据。
- **为什么日志是 JSON 行**：容器日志、宿主机文件、CI 输出是三条不同的去向，
  行式 JSON 三边都能读，也便于按 level 过滤；统一 UTC 是因为容器、CI、开发者本机时区不同，
  只有统一成 UTC，日志顺序才和真实顺序一致。
- **为什么接管 uvicorn 的 logger**：uvicorn 自己的 handler 写的是非结构化文本，
  与业务日志混在一起没法按字段查。接管时必须把 `propagate` 关掉，
  否则同一条记录会被写两遍（logger 自己一遍、传播到 root 一遍）。

## 代价

- 多一个 compose 文件与三份镜像/配置要维护；本机需要装 Docker。
- bind mount 意味着容器里的数据目录与宿主共享，不能拿它当隔离环境用。
- 接管 uvicorn 日志后，日志格式不再跟随 uvicorn 版本的默认格式。
- 日志落盘需要磁盘空间（10MB×5 轮转，上限约 60MB）。

## 推翻条件

- 需要多环境（预发/生产）跑同一套编排、彼此数据隔离时，bind mount 不够用，
  应换回命名卷，并把备份/巡检脚本改成能在容器内执行。
- 需要日志集中检索（ELK / Loki）时，JSON 行只是过渡格式，应直接接采集器。

## 后果

- `backend/.env` 被 `backend/.dockerignore` 排除，凭据只在运行时由 compose 的 `env_file` 注入；
  镜像里没有密钥，compose 文件里也没有。
- `JWT_SECRET` 缺失时后端拒绝启动——这是设计好的失败，不是崩溃。
- 宿主机上的 `scripts/ops/backup_db.py`、`scripts/ops/inspect_runtime.py` 针对的是
  容器正在用的那一份数据与日志，容器路径由 bind mount 对齐。
- **下载目录没有 bind mount**：容器里的下载产物落在镜像内的 `/app/downloads`，
  宿主机上的巡检看不到那一份。这是有意不做——加 bind mount 会撞上「宿主目录以 root
  属主创建 vs 容器里 uid 10001 写不进去」的权限问题。代价是：compose 部署形态下，
  巡检第 6 项查的是宿主机上的 `backend/downloads`（本机直接跑后端时的那一份），
  容器内那一份随容器销毁，不受它管。
- 运维手册的容器化章节见 `docs/OPERATIONS.md` 第 13 节。
