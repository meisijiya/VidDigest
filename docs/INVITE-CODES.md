# 邀请码：管理员怎么发码、码怎么活、用户说「邀请码有问题」时怎么办

注册需要邀请码。这份文档写给两拨人：**发码的管理员**，和**收到用户报错的人**。

设计决定见 [ADR 0023](adr/0023-invite-code-registration.md)。

## 一、管理员怎么发码

### 在管理后台发（推荐）

管理后台的「邀请码」区块里：

1. 点「展开邀请码」——列表是展开时才加载的，进后台不会替你打一次接口。
2. 填两个可留空的参数：
   - **可用次数**（默认 1）：这枚码能被注册几次。给一个人用填 1，给一个团队用可以填更多。
   - **有效小时数**（留空 = 永不过期）：过期后码自动失效，用户会看到「邀请码已过期」。
3. 「备注」是给自己看的（写「给张三」之类），不参与校验。
4. 点「生成邀请码」。

生成后界面上会出现**一串明文码**，旁边有「复制」按钮。**这串明文只出现这一次**：
刷新之后列表里只剩脱敏码（前后各 4 位，中间是 `****`），谁也拿不回完整码。
所以复制走之后立刻发给对方——发漏了只能作废重发一枚。

> **库里没有这串明文**。落库的是它的 sha256 摘要，加上一个给人看的脱敏提示。
> 库被读走不等于码被用掉——攻击者拿到的是摘要，反推明文只能猜，而码本身
> 够强（130 bit 的组合空间）。代价就是上面那句话：明文取不回来了。

### 用接口发

```
POST /api/admin/invite-codes
Authorization: Bearer <管理员的 token>
Content-Type: application/json

{ "max_uses": 1, "expires_in_hours": 24, "note": "给张三" }
```

三个键都可省：`max_uses` 默认 1，`expires_in_hours` 省略 = 永不过期，`note` 可空。
响应体里的 `item.code` 是明文码，只在这一次响应里出现。

值域不对（次数不是正整数、有效期不是正整数）会得到 400 与一句中文；请求体里有多余的
键会得到 422（结构错）。这两类错误码是有分工的：400 是「你写的值不对」，422 是
「你写的形状不对」。

### 看列表 / 作废

```
GET  /api/admin/invite-codes?limit=20&offset=0
POST /api/admin/invite-codes/{id}/revoke
```

列表里每行给出：脱敏码、状态、用量（用了 / 几次）、过期时间、备注。状态有四种：
**可用 / 已用完 / 已过期 / 已作废**。

作废是**幂等**的：同一枚码作废两次，两次都成功。作废只影响**之后**的注册，
已经用它建好的账号一律不动。

## 二、码的生命周期

```
                 ┌──────────────► 已用完（used_count 用满 max_uses）
                 │
   生成 ──► 可用 ─┼──────────────► 已过期（过了 expires_at）
                 │
                 └──────────────► 已作废（管理员 revoke）
```

- **可用** → 每一枚码诞生时都是可用的。
- **已用完**：`used_count` 达到 `max_uses`。用完就是用完，不会自己恢复。
- **已过期**：过了 `expires_at`。过期是**自然发生**的，不需要任何人操作。
- **已作废**：管理员手动撤的。这是唯一一个「本来还能用、被人为掐掉」的状态。

三条终态（用完 / 过期 / 作废）都是**不可逆**的。要再发一枚，生成新的。

`expires_at` 为空表示**永不过期**——那枚码会一直可用到用完或被作废为止。

## 三、用户说「邀请码有问题」时怎么办

注册失败时后端会给出四句不同的话。**别把它们混成一句「邀请码错误」**——用户据此能
行动，混了用户就只能干瞪眼。

| 用户看到的话 | 真实原因 | 该怎么办 |
| --- | --- | --- |
| 需要邀请码 | 没填，或填的是空格 | 让他去管理员那要一枚 |
| 邀请码无效 | 这枚码不存在（多半是抄错了，或者被清理过） | 让他照着原样重新抄一遍；仍不行就发新的 |
| 邀请码已作废 | 这枚码被管理员撤了 | 找管理员确认，然后发新的 |
| 邀请码已过期 | 过了有效期 | 找管理员重新发一枚（可以给个长一点的期限） |
| 邀请码已被用完 | 这枚码的次数用满了 | 找管理员发新的，或者让管理员把次数调大（老码不行，要新码） |

**最容易踩的一条**：一枚 `max_uses` 为 1 的码被 A 用掉之后，B 再拿同一枚去注册，看到的
就是「邀请码已被用完」——不是「邀请码无效」。这说明码本身是对的，只是轮到 B 时已经
用完了。

## 四、几条容易搞混的语义

- **明文只给一次**：库里存的是 **sha256 摘要**，不是明文——库被读走不等于码被用掉。
  明文只在生成那一次响应里出现，之后哪儿都取不回。想找回一枚发过的码，只能作废重发。
- **列表里的脱敏码不是码**：它是建码那一刻从明文算出来存下的提示（前 4 后 4，中间
  `****`），只够管理员认出「这枚是我发给张三的那枚」。它**不是明文**，拿去注册会得到
  「邀请码无效」——它也**不是**某种缩写形式，猜不出完整码。
- **注册失败不消耗码**：邮箱已存在、密码不合规这些失败**不会**把码的次数用掉。
  只有账号真的建成了，次数才 +1。所以「用同一枚码注册失败」之后再试一次，次数还是原样。
- **一个码同时只能被一个人用掉**：`max_uses` 为 1 的码被两个请求同时抢，
  只有一个成功，另一个拿到「邀请码已被用完」。注册是原子的，不会出现
  「码被消耗了但账号没建成」或者「账号建成了但次数没加」。
- **作废不会动已有账号**：码作废只让它不能再注册新账号；用它建好的账号不受影响。
- **邀请码不等于身份**：`max_uses` 大于 1 的码可以给多个人用，事后无法从账号反查是谁
  用掉了它。

## 五、老库怎么办

`invite_codes` 这张表在 `backend/database.py` 的 `init_db()` 里建，**老库也有升级路径**，
启动一次就够，不需要手工建表，也不需要停服：

- **表不存在**（工单 #99 之前的库）：建出来。
- **表在、列缺**（上一版发布时少写了列）：补齐。
- **表在、但存的是老结构**（工单 #99 之后、#103 之前的库，`code` 列存明文）：**重建这张表**。
  重建时把每一行的明文算成 sha256 摘要填进新表，所以——

  - **升级前发出的码仍然可用**（老用户不用重新要码）；
  - 升级之后库里**不再有明文邀请码**（连数据库文件的空闲页里也没有）；
  - 已用数、备注、创建时间原样保留。

所以：**升级只需要重启后端**。

升级前建议备份一份数据库文件：老库里的明文码本来就是「谁拿到库谁就能用」的状态，
备份一份不会更糟，但升级后它就只是一堆算不出明文的摘要了。
